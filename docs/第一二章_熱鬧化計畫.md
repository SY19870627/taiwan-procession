## 4. 故事臨場感：三種演出方式比較

現況：`StoryScene` 是「漸層底色＋遠景剪影＋立繪＋下方對話框」，`CutScene` 是 3～4 秒的程式動畫（起駕、日落、天亮、魔王現身）。兩者分開；劇情裡「發生了什麼」只能靠旁白文字講。

**沒有音效系統**（第三章計畫 Q22）是三種方式共同的限制：節奏、氣氛只能靠畫面。第三章已經用「咚！」字、霓虹閃光、畫面輕震代替鼓聲（決策 D79），這個做法三種方式都可以沿用；但越「靜」的方式（慢推的插畫）越吃音樂，沒有聲音時越容易顯得空。

| | (1) 分鏡插畫 | (2) 引擎內演出（**原型已做**） | (3) 圖示／剪影 |
|---|---|---|---|
| 看起來像什麼 | 每段過場 2～4 張繪本式插畫，鏡頭慢推慢移（Ken Burns），漫畫分格從旁滑入，字幕在下方 | 像現在的 `CutScene` 加上對話：背景、陣頭小人、轎、魔王在場上走位，頭上冒泡泡；鏡頭推近說話的人、震動、閃白、放鞭炮、狀聲字 | 皮影戲／廟牆壁畫感：黑底或宣紙底，剪影人物與圖示（旗、鎖鏈、王船、馬）淡入淡出、平移，配一行字 |
| 臨場感 | 高（畫面最漂亮、最有情緒） | 中高（「事情正在發生」，而且是遊戲裡同一批角色） | 中（有風格，但抽象，情緒要靠字） |
| 工作量（程式） | 2 階段：`Cutscene` 加 `panels` 欄位與播放器（Ken Burns、分格、字幕）；接三章 | 3～4 階段：把原型正式化（支援蓋在畫面上播、略過、退回文字版）；第一、二章腳本；第三章腳本（可選）；手機驗收 | 1～2 階段：剪影播放器＋腳本 |
| 工作量（腳本） | 每段挑 2～4 個畫面、寫字幕 | 每段要寫走位與鏡頭（約每句 1～3 行資料，見 `content/protoStage.ts`） | 每段挑 3～5 個圖示動作 |
| 畫師要畫 | **最多**：第一、二章 10～12 段過場 × 2～4 張 ≈ 30～40 張；三章一致再加第三章 8 段 ≈ 20～25 張。建議 1440×1080（橫圖，讓鏡頭有空間平移；直式畫面上下留字幕）webp，檔名 `public/story/<過場id>_<序號>.webp`，例 `recall_1.webp` | **少**：多數用現有圖。要補的是「演出用的全身小人」（判官、中軍府、巡捕全身，石駒跪姿、黑潮人形等，見 §5 B 組，約 10～14 張）；每章 1～2 張「關鍵大圖」可選 | 中：剪影 15～20 張（人物、陣頭、魔王、道具），512×512 去背單色 PNG／webp，`public/silhouette/<名稱>.webp`；也可以先用程式畫的小人塗黑當剪影 |
| 第三章 8 段能不能一致 | 可以，但要多畫 20～25 張；風格要跟第三章已交的正式背景、戰鬥圖一致 | **可以，而且最便宜**：第三章已有正式背景（`bg/`）、戰鬥圖（`battle/`）、五營立繪、蛟，腳本照寫即可 | 可以，但第三章已經有正式美術，改成剪影反而退步 |
| 效能／手機 | 風險最高：一張 1440×1080 解碼後約 6 MB 顯示記憶體，一段 4 張就 24 MB；要逐段載入、播完釋放，iOS Safari 記憶體吃緊；下載量增加 5～10 MB | 低：全部是已載入的貼圖，原型在桌機無頭瀏覽器順跑；鏡頭用「整個舞台容器縮放」，不另開相機 | 低：小圖、少量 |
| 維護 | 改劇情要重畫圖；台詞改了圖可能對不上 | 改台詞只改資料；角色換正式圖會自動套上（和現在立繪一樣「有圖就用圖」） | 改劇情只換圖示 |
| 和 `StoryScene`／`CutScene` 相容 | 可以做成 `Cutscene` 的可選欄位：有插畫就播插畫，沒有就是現在的文字版 | 同上：`Cutscene` 加可選的 `stage` 腳本；沒有腳本或載入失敗就退回文字版。台詞**直接引用原本的 `lines`**（原型的測試已經鎖住「台詞一字不差」），兩邊不會分岔。要補的是「蓋在畫面上播」（紙紮童跪下 `zhizha3` 用的 overlay） | 同上 |
| 沒有音效時的表現 | 最吃虧：慢推＋靜音容易像投影片 | 有動作可看，狀聲字（「鏘！咚咚！」）＋震動＋閃白能補一部分 | 節奏感要靠字，偏靜 |
| 主要風險 | 畫師產能、記憶體、風格一致 | 構圖：直式畫面下半部空，要練構圖（原型已把地平線放在 66% 高度）；小人是程式畫的，近看比較粗，關鍵時刻需要正式圖撐 | 風格和遊戲其他部分落差大，可能被當成「省錢版」 |

### 建議

**以 (2) 引擎內演出為主，每章挑 1～2 個最重要的瞬間用 (1) 的「關鍵大圖」補強。不採用 (3)。**

- (2) 用的是玩家已經看了一整章的同一批陣頭、轎、魔王，「剛剛跟我一起遶境的七爺八爺，現在就站在廟埕上」，臨場感來自連貫，而不是畫面精細。
- (2) 和方案 A 天然契合：隨從的互嗆可以直接變成過場裡的泡泡（原型 `recall` 就示範了七爺八爺插話）。
- 三章一致的成本最低：第三章的 8 段只要寫腳本，不用新畫圖。
- 美術需求最少，畫師可以專心先畫方案 A 的立繪；正式「全身小人」交了再換。
- 關鍵大圖（每章 1～2 張，例如「石駒跪在廟埕」「王船在海上燒」「太子收服蛟」）在 (2) 裡當成一個「定格」拍子播：鏡頭推到最近時切成插畫、慢推 3 秒、再切回來。這樣 (1) 的優點只花 4～6 張圖。
- 沒有音效：(2) 已經用狀聲字＋震動＋閃白，日後有音效系統時，腳本裡的 `fx`／`sfx` 欄位可以直接接聲音。

## 7. 原型：引擎內演出（`?proto=stage`）

- **檔案**：`src/content/protoStage.ts`（腳本資料）、`src/scenes/ProtoStageScene.ts`（播放器）、`tests/protoStage.test.ts`（腳本裡的原台詞要和 `CUTSCENES` 一字不差、原本每一句都有演到、補寫的要標 `draft`）。`BootScene` 加 4 行（`?proto=stage` 時進原型）、`main.ts` 註冊場景。
- **正式流程不受影響**：沒有任何正式場景會走到 `protoStage`；`CUTSCENES`、`StoryScene`、`CutScene`、`Dialogue` 都沒改。
- **怎麼看**：
  - 第一章喚回石駒（神明視角）：`?proto=stage`（等於 `?proto=stage&id=recall`）
  - 第一章石駒在山上（妖怪視角）：`?proto=stage&id=dusk3`
  - 點畫面一下進下一拍；右上「略過」回標題；右下「對照原本的過場」播現在的文字版，播完回到原型。
- **演了什麼**：
  - `recall`：惠澤宮廟埕，七爺、神轎、八爺在左，帶紫煞的石駒在右 → 七爺八爺小聲插話（補寫【待定】）→ 鏡頭推到神轎上方，「旨意」光圈＋「令」字降下，泡泡「回來吧。」＋閃白 → 鏡頭轉向石駒，紫煞散開、石駒換成平靜的樣子走近，「……主公。」→ 拉遠、鞭炮、「鏘！咚咚！」狀聲字。
  - `dusk3`：石駒從右邊走進山裡，紫煞變濃，鏡頭推近肚子的洞 → 鏡頭轉向山下，遶境的令旗、燈籠一盞盞亮（補寫旁白【待定】）→ 鏡頭猛推＋震動，「也是來鑿我的嗎？」
- **暫代美術**：全部是現有程式畫的貼圖（`qiye`、`baye`、`palanquin`、`shiju`、`shiju_calm`、`decree`、`temple_huize`、`mtnFarN`、`lantern`、`smoke`、`spark`）。
- **原型看到的問題**（S1 要處理）：直式畫面下半部比較空（之後可以把對話泡泡、旁白放下半部，或把地面上的人物放大）；程式畫的石駒近看很粗，正是 B 組「石駒跪」要補的；旨意光圈在暗底上偏亮。
